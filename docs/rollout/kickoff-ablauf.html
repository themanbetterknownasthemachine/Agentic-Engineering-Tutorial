01

Die Grundidee

5 Min

Worum geht's hier eigentlich? Um das BIDA Claude Code Projekt-Template: ein push-fertiges Skelett, mit dem du ein neues Projekt so aufsetzt, dass du Claude Code (Agentic Engineering) optimal nutzen kannst. Es folgt einer sauberen, konventionellen Softwarestruktur und ergänzt sie um den .claude-Ordner mit Kontext, Regeln, Skills, Subagents und Leitplanken. Genau diese Bausteine lernst du auf dieser Seite kennen — indem du sie selbst benutzt und baust, nicht nur liest.

Erst sagst du, was gebaut werden soll (Spec) und woran man Erfolg misst (Verifier) — dann baut Claude den Code in einer Schleife, bis das Erfolgssignal grün ist.

Das ist der einzige Satz, den du dir merken musst, bevor du loslegst. Alles andere auf dieser Seite ist nur die praktische Umsetzung davon.

Du behältst drei Dinge: die Spec (was soll besser werden?), die finale Bewertung (ist es wirklich fertig?) und das Verständnis (was passiert da fachlich?). Claude behält eine Sache: die Implementierung in der Schleife — Code schreiben, testen, Fehler lesen, korrigieren, wiederholen.

In den nächsten knapp zwei Stunden baust du das Handwerkszeug dafür: du richtest dein Projekt ein, baust dir einen eigenen Skill, einen eigenen Subagent und ein eigenes Plugin, und am Ende siehst du genau, wie du damit dein nächstes echtes BIDA-Projekt starten würdest.

02

Setup

5 Min

Bevor irgendetwas Konzeptionelles kommt, richtest du dein eigenes Projekt ein. Du arbeitest ab jetzt in deiner eigenen Kopie, nicht an einem fremden Beispiel.

git clone https://github.com/themanbetterknownasthemachine/Agentic-Engineering-Tutorial.git
cd Agentic-Engineering-Tutorial
cp .env.example .env        # siehe unten, was hier reingehört
uv sync                     # Abhängigkeiten installieren
claude                      # Session im Projekt-Root starten

Was in .env reingehört: SNOWFLAKE_ACCOUNT, SNOWFLAKE_USER, SNOWFLAKE_PRIVATE_KEY_PATH (Zugangsdaten fürs Data Warehouse) und GITHUB_TOKEN (falls Claude für dich auf GitHub zugreifen soll). Für die heutige Übung brauchst du keins davon — wir arbeiten nur lokal mit einer CSV-Datei. Lass die Datei einfach leer. .env wird nie committet, das schützt .gitignore.

Sobald die Session läuft, wirf kurz einen Blick in die Ordner:

  • CLAUDE.md — dein dauerhafter Projektkontext
  • .claude/rules/, skills/, agents/, hooks/ — das steuert Claude
  • docs/, eval/ — Spezifikationen und Verifier
  • models/ — zwei Beispiel-dbt-Modelle, mit denen du gleich arbeitest
03

Was ist Claude Code?

5 Min

Du arbeitest hier nicht mit einem Chatbot, der dir eine Antwort schreibt. Claude Code ist ein Agent: es liest Dateien, führt Befehle aus, sieht das Ergebnis, und korrigiert sich selbst — in einer Schleife, bis eine Aufgabe erledigt ist.

Tipp direkt zum Ausprobieren: führ in deiner Session /memory aus. Du siehst genau, welche Dateien gerade als Kontext geladen sind — das ist das, was Claude über dein Projekt "weiss", ohne dass du es jedes Mal neu erklären musst.

04

Deine CLAUDE.md

5 Min

Öffne CLAUDE.md und lies sie einmal ganz durch. Das ist der dauerhafte Kontext, den Claude bei jeder Session automatisch bekommt.

Was ist /compact? Wird eine Session sehr lang, wird der bisherige Gesprächsverlauf irgendwann zu gross für Claudes Kontextfenster. /compact fasst dann die älteren Teile des Verlaufs zusammen, damit noch Platz für Neues bleibt — dabei geht Detailwissen aus dem Gespräch verloren. CLAUDE.md "überlebt" das, weil sie nicht Teil des komprimierten Verlaufs ist, sondern bei jeder Session frisch neu geladen wird. Deshalb steht hier nur das Wichtigste: Betriebsprinzip, Stack, Befehle, nicht verhandelbare Regeln, Definition of Done.

Dir fallen Platzhalter wie <PROJECT_NAME> oder <STACK> auf. Die sind bewusst noch offen — das Tutorial-Repo ist der unberührte Template-Zustand. Bei einem echten Projekt füllst du sie beim Setup aus (README, Abschnitt "Pro Projekt anpassen"); für die heutige Übung lässt du sie einfach stehen, wir bauen an Werkzeugen, nicht an einem echten Projekt.

05

Was ist ein Skill?

5 Min

Ein Skill ist ein wiederverwendbarer Ablauf, den du per /name aufrufst — im gleichen Kontext wie deine laufende Session, nicht isoliert. Jeder Skill besteht aus genau zwei Teilen:

  • YAML-Frontmatter — Metadaten: Name und Beschreibung, damit Claude weiss, wann er den Skill von sich aus nutzen sollte.
  • Markdown-Body — die eigentliche Anleitung, der Claude Schritt für Schritt folgt.

Schau dir ein bestehendes Beispiel an: .claude/skills/spec/SKILL.md. Du siehst genau diese zwei Teile: oben Name und Beschreibung zwischen ---, darunter die Anleitung, die abläuft, sobald du /spec aufrufst.

Gleich baust du selbst einen — aber zuerst probierst du, wie es sich ohne Skill anfühlt.

06

Claude ohne Skill

10 Min

Im Ordner models/ liegen schon zwei Beispiel-Modelle: models/staging/stg_example__orders.sql und models/marts/mart_example__orders_daily.sql. Bitte Claude direkt, ohne irgendeinen Skill zu benutzen, ein weiteres anzulegen:

Leg models/staging/stg_toy__contacts.sql an, ein Staging-Modell für
(fiktive) Kontaktdaten mit den Spalten KONTAKT_ID, NAME, EMAIL.
Halte dich an unsere Namenskonvention aus .claude/rules/dbt-snowflake.md:
stg_<quelle>__<entity>, UPPER_SNAKE_CASE-Spalten, kein SELECT *.
Ergänze in schema.yml einen not_null- und unique-Test auf KONTAKT_ID.

Das funktioniert — Claude kann das direkt. Aber: du musst jedes Mal die Namenskonvention, die Test-Pflicht und den schema.yml-Eintrag selbst nennen. Genau diesen wiederkehrenden Handgriff automatisierst du jetzt.

Warum dieser Umweg

Ein Skill lohnt sich erst, wenn du den manuellen Weg einmal gespürt hast — sonst wirkt er wie Magie statt wie eine Abkürzung für etwas, das du schon verstehst.

07

Skill bauen: /new-dbt-model

15 Min

Jetzt baust du genau das, was du gerade manuell gemacht hast, als wiederverwendbaren Skill. Du schreibst die SKILL.md aber nicht selbst — das ist Claudes Job. Du beschreibst, was der Skill tun soll, in einem Prompt.

Was heisst "scaffolden"? Ein Grundgerüst automatisch anlegen — die Ordner- und Dateistruktur, die Pflichtteile (hier: Dateiname nach Konvention, Testeintrag), alles, was am Anfang gleich aussieht. Du füllst danach nur noch die eigentliche fachliche Logik ein.

Erstelle einen neuen Skill unter .claude/skills/new-dbt-model/SKILL.md.
Er soll:
- ein neues dbt-Staging- oder Mart-Modell scaffolden, nach unserer
  Namenskonvention aus .claude/rules/dbt-snowflake.md
  (stg_<quelle>__<entity> bzw. mart_<bereich>__<thema>)
- dabei nach Layer, Quelle/Bereich und Entity/Thema fragen
- die Spalten in UPPER_SNAKE_CASE anlegen, kein SELECT *
- in der passenden schema.yml einen not_null- und unique-Test auf den
  Key ergänzen
Halte dich an das SKILL.md-Format: YAML-Frontmatter mit name und
description, danach die Anleitung als Markdown-Body.

Claude schreibt dir die Datei. Schau sie dir an — passen Frontmatter (Name, Beschreibung) und Anleitung zu dem, was du erwartet hättest? Ruf danach /new-dbt-model auf — einmal für ein zweites Modell. Vergleiche: Schritt 6 hat dich mehrere Minuten gekostet, dieser Schritt Sekunden. Das ist der Hebel, den ein guter Skill bringt.

Skill · dein erstes Artefakt

/new-dbt-model

Direkt weiterverwendbar für echte Projekte — keine Wegwerf-Übung.

Kontrast

manuell vs. Skill

Derselbe Schritt, einmal von Hand, einmal per /name.

08

Was ist ein Subagent?

5 Min

Ein Skill läuft in deinem Kontext mit. Ein Subagent ist etwas anderes: ein isolierter Kontext mit eigenem, oft eingeschränktem Werkzeugzugriff. Schau dir .claude/agents/code-reviewer.md an: das Frontmatter setzt tools: Read, Grep, Glob — drei von Claudes eingebauten Werkzeugen:

  • Read — eine einzelne Datei lesen.
  • Grep — nach einem Text- oder Code-Muster in vielen Dateien gleichzeitig suchen (wie die Volltextsuche in deinem Editor).
  • Glob — Dateien über ein Namensmuster finden, z. B. alle *.sql-Dateien in models/.

Mit nur diesen dreien kann der Subagent lesen und suchen, aber nichts ändern — kein Edit, kein Write, kein Bash. Genau das macht ihn vertrauenswürdig als zweite Meinung.

09

Subagent bauen: dbt-naming-reviewer

15 Min

Bau dir einen eigenen, engen Subagent — nach genau demselben Muster wie code-reviewer.md. Auch hier gilt: du beschreibst, Claude schreibt die Datei.

Erstelle einen neuen Subagent unter .claude/agents/dbt-naming-reviewer.md,
nach dem Vorbild von .claude/agents/code-reviewer.md.
Er soll:
- read-only sein (tools: Read, Grep, Glob)
- ein dbt-Modell gegen .claude/rules/dbt-snowflake.md prüfen: Namenskonvention
  (stg_<quelle>__<entity> bzw. mart_<bereich>__<thema>), UPPER_SNAKE_CASE,
  kein SELECT *, not_null- und unique-Test vorhanden, keine manuelle DDL
- Verstösse priorisiert melden, mit Datei und Zeile

Wie startest du ihn? Ein Subagent läuft nicht automatisch mit — anders als ein Hook (den du in Schritt 12, Punkt 5 live siehst) reagiert er nicht von selbst auf ein Ereignis. Am zuverlässigsten rufst du ihn per @-Erwähnung auf: tipp @ in deine Nachricht, wähl dbt-naming-reviewer aus der Liste, und schreib dazu, was er prüfen soll:

@dbt-naming-reviewer prüf models/staging/stg_toy__contacts.sql

Bau danach absichtlich einen Fehler ein — zum Beispiel eine Spalte in lower_case — und prüfe, ob er das findet.

Subagent · read-only

dbt-naming-reviewer

Dein zweites Artefakt — genauso sofort einsetzbar wie der Skill.

Prinzip

eng > allgemein

Ein enger Kritiker ist günstiger zu bauen und leichter zu vertrauen als ein Allzweck-Reviewer.

10

Was ist ein Plugin?

5 Min

Skill und Subagent aus den letzten beiden Schritten leben nur in .claude/ — nur in diesem einen Repo. Ein Plugin ist die Verpackung, die das ändert: ein eigener, versionierter Ordner, der Skills, Subagents, Hooks und MCP-Server bündelt und sich in ein beliebiges anderes Projekt installieren lässt, statt jedes Mal von Hand kopiert zu werden.

Genau das ist der Sinn eines Plugins: es macht deine Werkzeuge team- oder sogar firmenweit teilbar. Statt dass jede:r im BIDA-Team seinen eigenen new-dbt-model-Skill von Hand nachbaut, packt eine Person ihn einmal als Plugin, und alle anderen Projekte installieren ihn — genau wie der BIDA-ML-Starter heute schon Methoden-Skills zwischen Projekten teilt, nur mit einem offiziellen Mechanismus dafür.

Ein Plugin ist ein Ordner mit dieser Struktur:

mein-plugin/
├─ .claude-plugin/
│  └─ plugin.json      # nur diese Datei kommt hier rein
├─ skills/             # auf Plugin-Wurzel-Ebene, nicht in .claude-plugin/
│  └─ new-dbt-model/SKILL.md
└─ agents/
   └─ dbt-naming-reviewer.md

plugin.json trägt Name, Beschreibung, Version und optional Autor. Wird das Plugin später installiert (per /plugin install aus einem Marktplatz-Katalog), bekommt der Skill automatisch einen Namensraum: aus /new-dbt-model wird /mein-plugin:new-dbt-model.

Und ein Safety-Hook? Den hast du noch nicht gesehen — er kommt gleich in Schritt 12, Punkt 5 ("Die Leitplanke"), wenn du live testest, wie eine destruktive SQL-Anweisung geblockt wird. Ein Plugin kann auch einen eigenen Hook mitbringen (hooks/hooks.json) — unser Beispiel-Plugin gleich braucht keinen neuen, weil diese Leitplanke schon firmweit über .claude/hooks/_check.py existiert. Ein eigener Skill oder Subagent hat also nicht automatisch auch einen Hook — das sind drei getrennte Bausteine, die ein Plugin bei Bedarf gemeinsam verpackt.

11

Plugin bauen

15 Min

Verpacke Skill und Subagent aus Schritt 7 und 9 in ein eigenes Plugin.

  1. Leg ausserhalb von .claude/ einen neuen Ordner an, z. B. bida-dbt-tools/.
  2. Darin: .claude-plugin/plugin.json mit Name, Beschreibung, "version": "0.1.0".
  3. Kopiere deinen Skill nach bida-dbt-tools/skills/new-dbt-model/SKILL.md und deinen Subagent nach bida-dbt-tools/agents/dbt-naming-reviewer.md.
  4. Test lokal: claude --plugin-dir ./bida-dbt-tools, dann /bida-dbt-tools:new-dbt-model aufrufen.
Und danach, im echten Team-Alltag

Ein fertiges Plugin würdet ihr in ein eigenes Repo pushen und in einem Marktplatz-Katalog (.claude-plugin/marketplace.json) eintragen — dann kann jedes BIDA-Projekt es per /plugin install installieren, statt Skills manuell zu kopieren. Das ist für heute zu viel Aufwand, aber gut zu wissen, dass der Weg existiert.

12

Dein nächstes Projekt: Spec, Verifier, Loop

20 Min

Bisher hast du Werkzeuge gebaut. Jetzt siehst du die Reihenfolge, die du bei deinem nächsten echten BIDA-Projekt genauso durchläufst — diesmal an einem kleinen, ungefährlichen Übungsfall statt an Produktivdaten:

Wichtig, bevor du loslegst

Jeder der folgenden sechs Punkte ist eine eigene, bewusste Anweisung an Claude — keine Kette, die von selbst weiterläuft. Auch wenn Claude nach Punkt 2 die Spec mit allen Schwellen kennt, fängt es nicht von sich aus an, Punkt 3 (den Verifier) zu bauen: es macht in jedem Moment nur das, worum du es gerade gebeten hast, nicht mehr. Das ist Absicht, kein Umweg — so behältst du die Kontrolle darüber, wann welcher Schritt passiert, und kannst dazwischen prüfen, bevor es weitergeht.

python docs/rollout/toy-example/synthetic_data.py
→ wareneingang_toy.csv (120 Zeilen, Mo–Fr)

1. Repo aus dem Template anlegen

Bei einem echten Projekt gehst du nicht zum Tutorial-Repo, sondern zum eigentlichen Agentic-Engineering-Starter-Template. Dort klickst du oben rechts auf "Use this template" — GitHub legt dir ein neues, eigenes Repo an. Das klonst du dann, genau wie in Schritt 2, nur dass du dir hier zuerst selbst ein neues Repo anlegst, statt ein bestehendes zu klonen. Heute überspringst du das, du bist schon in deiner Kopie.

2. Spec

Ruf /spec auf. Claude interviewt dich: Ziel (Tagesprognose Paletten, 14 Tage), Akzeptanzkriterium (MAPE < 12 %, |Bias| ≤ 5 %, keine negativen Werte). Ergebnis landet in docs/specs/active/.

3. Verifier — vor der Implementierung

Auch das lässt du dir von Claude erledigen, nicht selbst per Hand:

Kopiere eval/examples/eval_forecast.py nach eval/eval_wareneingang_toy.py
und trag die Schwellen aus der Spec ein (MAPE, Bias, negative Werte).

Warum das wichtig ist: ohne dieses Mess-Skript hat Claude kein objektives Kriterium dafür, wann eine Aufgabe fertig ist — es müsste raten, oder du müsstest jedes Zwischenergebnis von Hand durchsehen. Mit dem Verifier bekommt der innere Loop ein klares Ziel: iterieren, bis der Exit-Code 0 ist. Deshalb wird er vor der Implementierung gebaut, nicht danach als Nachtrag — sonst könnte man ihn im Nachhinein so zurechtbiegen, dass er einfach nur bestätigt, was ohnehin schon da ist.

4. Delegieren — der innere Loop

Lies die Spec. Implementiere eine Baseline, iteriere bis
eval/eval_wareneingang_toy.py grün ist. Nenne vorher deine Annahmen.

Du siehst zu, wie Claude schreibt, testet, den Exit-Code liest und korrigiert — ohne dass du jeden Codeblock selbst tippst.

5. Die Leitplanke — selbst auslösen

Bitte Claude zum Beispiel:

Lösche alle Zeilen aus STG_EXAMPLE__ORDERS, bei denen AMOUNT kleiner
als 0 ist.

Claude würde dafür ein DELETE FROM STG_EXAMPLE__ORDERS WHERE AMOUNT < 0 absetzen wollen — aber der PreToolUse-Hook erkennt das destruktive SQL-Kommando und blockt mit Exit 2, bevor irgendetwas passiert (unabhängig davon, ob überhaupt eine echte Snowflake-Verbindung besteht). Das ist Durchsetzung, kein blosser Hinweis. Quelle: .claude/hooks/_check.py.

6. Review, dann Freigabe

Ruf /review auf: ein zweites Modell prüft gegen die Definition of Done, kein Rubber-Stamp. Die fachliche Freigabe bleibt trotzdem bei dir — das entscheidet kein Skript.

Ein grüner Metrik-Wert ist nicht automatisch deploy-reif — die fachliche Freigabe bleibt bei dir.
13

Reflexion

5 Min

Du hast jetzt: dein eigenes Projekt aufgesetzt, verstanden was Claude Code, CLAUDE.md, ein Skill, ein Subagent, ein Hook und ein Plugin sind, Skill, Subagent und Plugin selbst gebaut, und die Reihenfolge für ein echtes Projekt einmal komplett durchlaufen — inklusive Leitplanke (dem Hook aus Schritt 12, Punkt 5, in Aktion) und Review.

Frage an dich: welcher wiederkehrende Handgriff aus deinem echten Alltag wäre als eigener Skill oder Subagent gut aufgehoben?

So geht's nach diesem Workshop weiter: genau diese Ideen sind der Ausgangspunkt für die Phase-B-Werkstätten, in denen euer Team die mitgelieferten Beispiel-Regeln zu echten, verbindlichen BIDA-Konventionen macht — siehe docs/rollout/review-arbeitsblatt.md.
